# MyOwnBank — план проекта

Цель: пет-проект уровня «можно защитить на собеседовании в финтех».
Стек: Python 3.14, FastAPI, SQLAlchemy 2.0, Alembic, PostgreSQL, pytest, scikit-learn, Docker, GitHub Actions.

Главный принцип: **сначала корректность денег и тесты, потом API, потом ML.**
Проект без тестов и с `float` вместо `Decimal` на собеседовании убивает впечатление сильнее, чем отсутствие ML.

### Баги и замечания в уже написанном коде

Разобрать до того, как двигаться дальше — это Этап 1.

1. **`SavingsAccount._validate_withdrawal` — инвертированное условие.**
   `if not self.__withdrawal_this_month >= MAX: raise` — исключение летит, когда лимит
   *не* исчерпан. Должно быть `if self._withdrawals_this_month >= MAX: raise`.
2. **Счётчик снятий нигде не увеличивается** и никогда не сбрасывается в начале месяца.
   Нужен либо `reset_monthly_counters()`, либо хранение `(year, month)` последнего снятия.
3. **Сеттер `interest_rate` ничего не присваивает** — только валидирует. Значение теряется.
   Плюс проверки в `__init__` дублируют сеттер: `__init__` должен вызывать сеттер.
4. **`BaseAccount.withdraw` проверяет баланс до `_validate_withdrawal`.**
   Из-за этого наследник физически не может разрешить овердрафт, а проверка в
   `CheckingAccount._validate_withdrawal` — мёртвый код. Правильно: базовый класс проверяет
   только «сумма валидна», а *можно ли уйти в минус* решает наследник.
5. **`__slots__` объявляет `__transaction_history`, но оно не инициализируется** —
   обращение к нему даст `AttributeError`.
6. **`from src.exceptions import *`** в `savings_account.py` — заменить на явный импорт.
7. **Нет защиты от `float`/`int`.** `deposit(10.5)` уронит код с `TypeError` из недр Decimal
   вместо доменного `InvalidAmountError`. Нужен единый валидатор суммы.
8. **Нет квантования до копеек.** `Decimal("0.0")` вместо `Decimal("0.00")`, нигде нет
   `.quantize(Decimal("0.01"), ROUND_HALF_UP)`. Для банка это обязательный инвариант.
9. **`InvalidAmountError` используется там, где смысл — «неверная ставка»** (`SavingsAccount.__init__`).
   Должен быть `InvalidInterestRateError`.
10. **`datetime.now()` в тексте исключения** — сообщение об ошибке зависит от времени вызова,
    такое невозможно нормально протестировать. Передавать период явно.

      Деньги в БД — **`Numeric(18, 2)`**, никогда не `Float`
- [ ] **Двойная запись (double-entry ledger).** Каждая операция — минимум две записи:
      дебет и кредит, сумма всех записей по проводке = 0. Баланс счёта = сумма проводок

      в финтехе, и главный технический «крючок» проекта.

- [ ] Alembic: `alembic init`, первая миграция, `make migrate`
- [ ] SQLite для локальной разработки, PostgreSQL в `docker-compose`

**Зачем в резюме:** SQLAlchemy 2.0, миграции, паттерны доступа к данным, бухгалтерская модель денег.

## Этап 5. ML — кредитный скоринг (~1 неделя)

Ключевая мысль: важна не модель, а то, что вокруг неё.

- [ ] Данные: German Credit (UCI), Home Credit Default Risk (Kaggle) или синтетика
      на основе транзакций из своей же БД
- [ ] `sklearn.Pipeline`: `ColumnTransformer` (импутация, OHE, скейлинг) + модель.
      Без пайплайна будет утечка данных, и это заметят
- [ ] Модели: baseline `LogisticRegression` → `GradientBoosting`/`LightGBM`
- [ ] **Метрики финтеха, а не accuracy:** ROC-AUC, PR-AUC, Gini, KS-статистика,
      матрица ошибок при выбранном пороге
- [ ] **WoE / IV** и скоринговая карта — язык кредитного риск-менеджмента
- [ ] Калибровка вероятностей (`CalibratedClassifierCV`) — банку нужна честная PD,
      а не просто ранжирование
- [ ] Выбор порога по ожидаемым потерям, а не по F1
- [ ] Интерпретируемость: SHAP или коэффициенты скоркарты → «причины отказа»
      (это ещё и требование регуляторов)
- [ ] Сохранение модели (`joblib`) + версия модели в ответе API
- [ ] `POST /credit/score` — скоринг заявки
- [ ] `MODEL_CARD.md`: данные, метрики, ограничения, риск смещения (bias)

**Зачем в резюме:** это то, что отличает «сделал модельку в ноутбуке» от «сделал ML в продукте».

## Порядок работы и приоритеты

Если времени мало, минимально достаточная версия для резюме — этапы 0–4 + 7 + 8.
ML (этап 5) добавляет ценности, но только поверх работающего бэкенда.

| Приоритет | Этапы | Почему |
|---|---|---|
| Критично | 0, 1, 2, 3 | Деньги, тесты, транзакции — база, без которой остальное не имеет смысла |
| Высокий | 4, 7, 8 | Без API и README проект нельзя показать |
| Средний | 5 | Отличает от обычного CRUD |
| Низкий | 6 | Приятный бонус |

Правило коммитов: одна логическая единица на коммит, тесты в том же коммите, что и код.
История коммитов — часть портфолио, её будут смотреть.
